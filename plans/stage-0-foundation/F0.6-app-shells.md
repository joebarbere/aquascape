# F0.6 — App shells (web + Electron)

**Stage:** 0 — Foundation & Walking Skeleton
**Owner:** `electron-platform-engineer` (Electron half), `angular-feature-engineer` (web half)
**Collaborators:** `renderer-engineer`, `test-engineer`
**Status:** Not started

## Goal

Two app shells that boot, host a canvas attached to `renderer-2d`, and show an empty tank. The Electron shell loads the web build with the full secure-defaults posture.

## Spec reference

Plan §2 (architecture), §3 (Electron security), Stage 0 F0.6.

## Dependencies

**Requires:** F0.1, F0.4 (renderer to attach), F0.5 (platform stubs).
**Enables:** F1.x and beyond (every feature lands inside these shells).

## Scope

### `apps/web/`

**In:**

- Angular standalone-component app with `OnPush` change detection by default.
- A root component hosting a full-window `<canvas>` element.
- App composition root binds `platform-api` tokens to `platform-web` implementations.
- On boot, instantiate a `Canvas2DRenderer`, `attach` it to the canvas, and `render` an empty scene (default tank ~600×360×360 mm) into a default viewport that centers the tank with comfortable padding.
- Window-resize handler re-`render`s on resize (no scroll, no zoom for now).
- Tag: `scope:app`.

**Out:**

- Tool palette, panels, menus — incremental from Stage 1.
- PWA manifest / service worker — F6.4.

### `apps/desktop/`

**In:**

- Electron app (Node.js main + preload + renderer).
- **Security posture (non-negotiable):**
  - `contextIsolation: true`
  - `sandbox: true`
  - `nodeIntegration: false`
  - `nodeIntegrationInWorker: false`
  - `nodeIntegrationInSubFrames: false`
  - No `remote` module.
  - Renderer's only path to native APIs is a typed preload bridge exposed via `contextBridge.exposeInMainWorld`.
  - CSP set on the loaded HTML; no `unsafe-eval`, no inline scripts in prod builds.
- Main-process boot: create a `BrowserWindow` with the above `webPreferences`, load the web build's `index.html` (file:// in prod, dev server in dev).
- Preload bridge **scaffolded** with a typed shape, even though there are no real channels yet. A `ping`/`pong` channel is fine to prove the bridge works end-to-end.
- App composition root binds `platform-api` tokens to `platform-electron` implementations (still stubs at this stage).
- Tag: `scope:app`.

**Out:**

- Real IPC channels for file IO — F1.4.
- Native menus / accelerators — incremental.
- Code signing, installer packaging — F6.4.
- Auto-updater — post-v1.

## Acceptance criteria

- [ ] `nx serve web` boots the web app to a window showing the empty tank.
- [ ] `nx run desktop:serve` (or equivalent) boots the Electron app to a window showing the same empty tank.
- [ ] The pixel output of web and desktop at the same window size matches (visual diff acceptable within anti-aliasing tolerance).
- [ ] **Security:** an automated test instantiates the Electron `BrowserWindow` and asserts every required `webPreferences` flag is set as specified.
- [ ] **IPC handshake:** the preload `ping` returns a `pong` value from the main process, validated in the desktop e2e test.
- [ ] Window resize re-renders the canvas (verified manually + via a Playwright test).
- [ ] No console errors, warnings, or CSP violations in either shell at boot.

## Testing

- **Unit:** composition-root wiring (correct platform binding chosen).
- **Component:** the root canvas component attaches/detaches the renderer on `ngOnInit`/`ngOnDestroy` cleanly.
- **E2E (Playwright web + Playwright-Electron):**
  - App boots, a tank is visible (pixel check on the tank rectangle area).
  - Window resize re-renders.
  - On desktop: preload `ping → pong` round-trips, asserting the typed bridge works.
  - On desktop: `webPreferences` check (security regression guard).

## Notes

- **Don't bake any platform-specific code into `apps/web` that should live in `platform-web`** — and same for desktop. The shells are thin; the platform abstraction does the lifting.
- **Dev workflow.** Document in `CLAUDE.md` how to run web + desktop concurrently (Electron typically points its renderer at the web dev server during development).
- **Capability detection.** The shell decides which platform implementation to use based on environment, not feature flags — `apps/web` always binds `platform-web`; `apps/desktop` always binds `platform-electron`. No runtime negotiation.
