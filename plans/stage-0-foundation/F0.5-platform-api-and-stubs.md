# F0.5 — platform-api + stub platform-web / platform-electron

**Stage:** 0 — Foundation & Walking Skeleton
**Owner:** `electron-platform-engineer`
**Collaborators:** `angular-feature-engineer`, `test-engineer`
**Status:** Not started

## Goal

Define the platform abstraction interface once, and ship in-memory stub implementations for both web and Electron so the editor can be built feature-by-feature without forcing real IO decisions before they're needed.

## Spec reference

Plan §2.5 (platform abstraction), Stage 0 F0.5.

## Dependencies

**Requires:** F0.1.
**Enables:** F0.6 (apps inject a concrete platform), all later features that touch IO / dialogs / storage.

## Scope

**In, in `libs/platform/platform-api/`:**

- **No implementation.** Interface library only.
- Interfaces with explicit, narrow capabilities:

  ```ts
  interface FileService {
    openDocument(): Promise<{ id: string; bytes: Uint8Array; name: string } | null>;
    saveDocument(args: {
      id?: string;
      bytes: Uint8Array;
      suggestedName: string;
    }): Promise<{ id: string } | null>;
    saveDocumentAs(args: {
      bytes: Uint8Array;
      suggestedName: string;
    }): Promise<{ id: string } | null>;
  }

  interface DialogService {
    confirm(args: { title: string; message: string; danger?: boolean }): Promise<boolean>;
    alert(args: { title: string; message: string }): Promise<void>;
  }

  interface StorageService {
    get<T>(key: string): Promise<T | null>;
    set<T>(key: string, value: T): Promise<void>;
    remove(key: string): Promise<void>;
  }

  interface RenderExportService {
    exportPng(args: { bytes: Uint8Array; suggestedName: string }): Promise<{ path: string } | null>;
  }
  ```

- Injection tokens for Angular consumption (in a sub-entry to avoid Angular leaking into the interface itself — e.g. `platform-api/angular`).

**In, in `libs/platform/platform-web/`:**

- Stub implementations backed by in-memory `Map`s and `URL.createObjectURL` for export. Real File System Access API + IndexedDB integration lands in F1.4 / F1.5; the stubs let other features develop against the interface meanwhile.
- Tag: `scope:platform-web`.

**In, in `libs/platform/platform-electron/`:**

- Stub implementations identical in shape to `platform-web`'s stubs (in-memory) but structured to be replaced by IPC calls in F1.4. **The Electron-side IPC channels are NOT wired in Stage 0** — that's F0.6 / F1.4. The stubs do everything in the renderer process for now.
- Tag: `scope:platform-electron`.

**Out:**

- Real file dialogs / file IO (web: F1.4; Electron: F1.4).
- IndexedDB / userData persistence for autosave (F1.5).
- OS secure storage for AI keys (F9.x).
- IPC handlers and the typed preload bridge (F0.6 handles the bridge scaffold; real channels in F1.4+).

## Acceptance criteria

- [ ] `platform-api` has tag `scope:platform-api` and contains **no implementation** — interfaces and Angular tokens only.
- [ ] `platform-web` has tag `scope:platform-web`; features cannot import it (boundary lint blocks).
- [ ] `platform-electron` has tag `scope:platform-electron`; features cannot import it.
- [ ] Each stub satisfies the interface and round-trips data via in-memory storage in tests.
- [ ] No platform implementation pulls in Angular, NgRx, or the renderer.

## Testing

- **Unit:** stub round-trip — `save` then `open` returns the bytes; `set` then `get` returns the value; `remove` clears it.
- **Boundary lint:** add a deliberate violation in a test PR (a `features/*` lib importing `platform-electron`) and verify CI rejects it.
- **E2E:** none specific; covered by F0.6 boot test using the stubs.

## Notes

- **Why a separate `platform-api/angular` entry point.** Angular `InjectionToken` lives in `@angular/core`; the pure-TS `platform-api` must not depend on Angular. Sub-entries (`platform-api/angular`) let the framework-free interface stay clean while still providing ergonomic Angular DI in feature libs.
- **Don't pretend the stubs are real.** They're labeled as stubs in their package READMEs and in code comments. F1.4 swaps them.
- **Capability flags.** If a stub can't fulfill a call (e.g. there's no real file to export), it should return `null` cleanly rather than throwing — feature code learns to handle the absent capability via the same null path that real implementations use when the user cancels a dialog.
