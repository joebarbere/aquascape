# F0.1 — Nx Monorepo Scaffold

**Stage:** 0 — Foundation & Walking Skeleton
**Owner:** `nx-workspace-engineer`
**Collaborators:** (none — this is the foundation everyone else builds on)
**Status:** Not started

## Goal

Stand up the Nx workspace with the exact directory layout from plan §2.1, with module-boundary tags configured so the layering rules from §2.2 fail CI on violation.

## Spec reference

Plan §2.1 (directory layout), §2.2 (layering & dependency rules), §3 (tooling), Stage 0 F0.1.

## Dependencies

**Requires:** none.
**Enables:** every other feature.

## Scope

**In:**

- Initialize an Nx workspace at the repo root (the existing planning artifacts must remain in place and continue to live at the repo root unless explicitly moved).
- Configure `pnpm` as the package manager (or `npm` if a strong reason exists — document the choice).
- Create the full directory skeleton from plan §2.1:
  ```
  apps/        web/  web-e2e/  desktop/  desktop-e2e/
  libs/
    domain/    scene-model/  document/  catalog/  growth-sim/  geometry/
    rendering/ renderer-api/  renderer-2d/  renderer-3d/
    features/  editor-shell/  tank-setup/  substrate-tool/  hardscape-tool/
               planting-tool/  layers-panel/  templates/  export/  livestock-equipment/
    ui/
    state/
    platform/  platform-api/  platform-web/  platform-electron/
    testing/
  tools/
  ```
  Empty libs are fine — `@nx/js:lib` with a stub `index.ts`. The goal is that the dependency graph and module boundaries are configurable from the first commit.
- Configure `@nx/enforce-module-boundaries` with the scope tags described in `.claude/agents/nx-workspace-engineer.md`:
  - `scope:domain` (may depend on `scope:domain` only)
  - `scope:rendering` (may depend on `scope:domain`)
  - `scope:feature` (may depend on `scope:domain`, `scope:rendering`, `scope:ui`, `scope:state`, `scope:platform-api`)
  - `scope:ui`, `scope:state`, `scope:platform-api`
  - `scope:platform-web`, `scope:platform-electron` (only `scope:app` may import these)
  - `scope:app`
- TypeScript strict mode everywhere. `tsconfig.base.json` enables strict, noImplicitAny, exactOptionalPropertyTypes, noUncheckedIndexedAccess.
- Jest preset wired for every lib.
- Prettier + ESLint configured at the workspace root.
- Update `CLAUDE.md`'s "Development commands" section with the real commands that now exist (`pnpm install`, `nx serve web`, `nx test <lib>`, `nx affected -t lint test build`, `nx graph`).

**Out (deferred):**

- Actual implementation inside any lib (covered by F0.2 onward).
- CI pipeline configuration — that's F0.7 (but same agent).
- Renderer / Angular / Electron generators (`@nx/angular`, `nx-electron`) can be added now or as part of F0.4/F0.6 — agent's discretion; document the choice.

## Acceptance criteria

- [ ] `pnpm install` succeeds on a clean clone.
- [ ] `nx graph` shows the full set of libs with the layering edges intended by the plan (and _no_ unintended edges from skeletal stubs).
- [ ] `nx lint` passes on every project.
- [ ] A deliberate boundary violation (e.g. importing `platform-electron` from a `features/*` lib) fails the lint check with a clear error.
- [ ] `nx test` runs (zero or trivial tests are fine) on every project.
- [ ] TypeScript `strict` is enforced and unviolated.
- [ ] `CLAUDE.md` "Development commands" section is updated with the real commands.
- [ ] All planning artifacts at the repo root (`aquascape-development-plan.md`, `aqua-document.ts`, `aqua-document.schema.json`, `example.aqua.json`, `.claude/`, `CLAUDE.md`, `plans/`) remain in place.

## Testing

- **Unit:** none required for the scaffold itself.
- **Integration:** the deliberate boundary-violation test described above. Either as a CI guard or as a documented manual check that the agent ran before merging.
- **E2E:** none in this feature; F0.6 / F0.7 cover boot tests.

## Notes

- **Decision: pnpm vs npm.** Nx supports both; pnpm has better install perf and stricter dependency hygiene. Recommend pnpm; if there's a reason to use npm, document it in an ADR.
- **Decision: nx-electron vs custom.** `nx-electron` is a community plugin; alternatively a hand-rolled Electron app project. Either works — the choice affects F0.6, not this feature, but agent should flag it.
- **Decision: standalone Angular vs NgModules.** Plan §3 says standalone components. Configure the Angular generator defaults accordingly when adding `@nx/angular`.
- Don't add features / domain logic in this PR. The scaffold is its own deliverable.
