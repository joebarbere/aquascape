# F10.1 — Three.js renderer (renderer-3d)

**Stage:** 10 — 3D Renderer
**Owner:** `renderer-engineer`
**Collaborators:** `scene-model-engineer`, `aqua-document-guardian`, `test-engineer`
**Status:** Not started

## Goal

Drop in a Three.js / WebGL renderer that implements the **same** `SceneRenderer` interface as `renderer-2d`, consuming the same canonical 3D coordinates already in the `.aqua` document. This is the architecture's final exam: no changes to `domain/scene-model`, no changes to the document format, just a new renderer.

## Spec reference

Plan §2.4, Stage 10 F10.1.

## Dependencies

**Requires:** Stages 0–9 stable (architecture must be solid).
**Enables:** F10.2 (toggle), F10.3 (3D assets).

## Scope

**In, in `libs/rendering/renderer-3d/`:**

- `WebGLRenderer implements SceneRenderer` using Three.js.
- Scene → Three.js mapping:
  - Tank → a transparent glass `Mesh` with refractive material (simple at v1; physically-correct refraction is out of scope).
  - Substrate → extruded shape from the profile.
  - Hardscape → meshes from `meshRef` (F10.3) or extruded billboards from `outline` polygon.
  - Plants → billboards or meshes depending on availability.
  - Layer opacity / visibility → applied at the group level.
- Camera: `PerspectiveCamera`. Default position: front-and-slightly-elevated view.
- Lighting: a few configurable lights (ambient + key + fill); a "tank-light" overhead default.
- `RenderSurface` extension: 3D needs the same `HTMLCanvasElement` (WebGL context) plus a `gl` extension probe.
- Performance budget: 60fps with the default starter scene; document a guideline on object count for sustained 60fps on mid-tier hardware.

**Out:**

- True caustics / volumetric water — out for v1.
- Physically-based plant simulation — out.
- VR / AR — out.

## Acceptance criteria

- [ ] `WebGLRenderer` implements `SceneRenderer` without modifying the interface.
- [ ] **Zero changes to `domain/scene-model` or `aqua-document.ts`** — the same document opens in 2D and 3D.
- [ ] Performance budget met for the default scene; sustained 60fps tracked in CI (or at least in a manual benchmark).
- [ ] `dispose` cleanly releases WebGL resources (verified via context loss + recovery test).
- [ ] Hit-test in 3D returns equivalent `HitResult` to the 2D version for objects in roughly the same screen position.

## Testing

- **Unit:** scene→Three.js mapping; camera math; lighting setup.
- **Integration:** render a known scene to a canvas, snapshot the framebuffer, compare against reference (tolerance ε for floating-point GPU variance — document the choice).
- **Component:** renderer switch preserves selection / document state.

## Notes

- **The architecture validation.** Plan §7 is explicit: "if the 3D renderer drops in without touching `domain/*`, the core abstractions were correct." If you find yourself needing to add fields to `Scene` or the document for 3D, **stop** and surface that to the architecture team. It's a signal that an abstraction is wrong, not that you should bypass it.
- **Three.js version pin.** Pin the major version and document upgrades carefully — Three.js has historically broken API across versions.
- **WebGL vs WebGPU.** WebGL 2 is the safe target for 2026. WebGPU adoption is uneven; defer.
