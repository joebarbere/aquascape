# F2.4 — Catalog loader

**Stage:** 2 — Substrate Tool
**Owner:** `catalog-engineer`
**Collaborators:** `electron-platform-engineer` (catalog-root config), `test-engineer`
**Status:** Not started

## Goal

Ship the first version of the catalog loader: reads catalog manifests from configurable roots, validates against per-type JSON Schemas, exposes a resolver for `CatalogRef` → catalog entry. Substrate is the first content type to consume it; tanks (F1.1) and later content types follow the same pattern.

## Spec reference

Plan Stage 2 F2.4; `CatalogRef` shape in `aqua-document.ts`.

## Dependencies

**Requires:** F1.3 (CatalogRef type), F0.5 (platform storage for user catalog roots).
**Enables:** every content-type feature from now on (tanks, hardscape, plants, livestock, equipment).

## Scope

**In, in `domain/catalog/`:**

- Manifest envelope schema:
  ```json
  {
    "catalog": "core",
    "version": 1,
    "entries": { "substrates": [...], "tanks": [...], ... }
  }
  ```
  Catalog namespaces (`"core"`, `"community:*"`) prevent id collisions.
- Per-type entry schemas (substrate now; tanks/hardscape/plants/etc. as those features land).
- Loader:
  - `loadCatalog(source): Promise<LoadResult>` — accepts a JSON string, a Uint8Array (ZIP of manifest + assets), or a URL.
  - Validates the envelope and every entry against the appropriate type schema.
  - Returns both the successfully-loaded entries and a list of `EntryValidationError`s with `{ index, idPath, message }` — the loader does NOT silently drop invalid entries; it surfaces them.
- Resolver:
  ```ts
  function resolveRef(
    refs: Catalog[],
    ref: CatalogRef,
  ): Result<CatalogEntry, CatalogResolutionError>;
  ```
  Deterministic given a catalog list order; returns a typed error (`UnknownCatalog`, `UnknownId`, `UnknownVersion`) rather than throwing.
- Cache: loaded catalogs are immutable; a `CatalogCache` interns them keyed by namespace.

**In, in `platform-api`:**

- A `CatalogService` interface for telling the loader where user / community catalogs live (a list of paths or URLs). `platform-web` reads from a configured location (or none in v1.x); `platform-electron` reads from `userData/catalogs/`.

**Out:**

- Community-catalog installer UI — post-v1.
- Catalog auto-update / signing — post-v1.

## Acceptance criteria

- [ ] The `core` substrate catalog ships in this repo and loads cleanly.
- [ ] An intentionally malformed manifest fixture produces validation errors with field paths, and the rest of the manifest loads.
- [ ] `resolveRef` returns typed errors for missing catalog / id / version.
- [ ] No Angular imports in the loader; lib has tag `scope:domain`.
- [ ] Catalog cache is verified idempotent: loading the same manifest twice returns the same entry references.

## Testing

- **Unit:** envelope validation; entry validation per type; resolver behavior on miss / version-miss / hit; deterministic resolution order with multiple catalogs.
- **Property tests:** a manifest with N valid + M invalid entries loads N successes and surfaces M errors, regardless of order.
- **Component / E2E:** picking a substrate by `CatalogRef` resolves correctly and the chosen material renders.

## Notes

- **`CatalogRef.version` semantics.** If a doc references `version: 1` of a substrate and the loaded catalog only has `version: 2`, the loader returns `UnknownVersion`. Features decide how to degrade (fall back to a placeholder + warning). Don't silently substitute.
- **Stable ids.** Once shipped, an id never changes meaning. New plant species → new id, not a renamed old id. Document this loudly in `provenance.md`.
- **Asset paths.** Catalog entries reference assets (thumbnails, meshes) via relative paths inside the manifest's ZIP. The loader exposes a `getAsset(catalog, path)` helper that platform implementations back with their storage.
