# Catalog caveats

**Load this when:** touching `libs/domain/catalog/` — adding entry kinds, schema branches, or authoring JSON manifests.

- **Invalid entries are surfaced, never silently dropped** (Plan §3). Duplicate `(catalog, id)` pairs become warnings, first-seen wins.
- **No fabricated tank presets.** `tank-presets.ts` documents every source. The four UNS sizes (9S, 45F, 75L, 120L) that don't exist in any verifiable source are **explicitly skipped, not invented** — same rule for the ADA Mini-S US/EU discrepancy (we follow ADA-NA spec) and the "5 gal cube" vendor variance.
- **Catalog growth is data-only.** Drop new JSON manifests into `libs/domain/catalog/src/data/<kind>/`, extend `core-catalog.ts` imports. The loader picks them up at module-import time. The schema's `oneOf` makes adding new `kind`s additive.
- **Livestock catalog fields are advisory, not enforceable.** `temperatureRange.minC < maxC` (and the equivalent for `pHRange`) is documented in the schema's `description` but the JSON-Schema spec can't express cross-field comparisons declaratively — the manifest authors are trusted. Same pattern other catalog kinds use ("schema is shape, semantics are advisory"). `bioloadClass` is a coarse three-bucket classifier intended as input to F7.2's stocking rules — not a quantitative gallons/fish formula. Don't fabricate species data: pick conservative numbers from well-known hobbyist sources (SeriouslyFish, manufacturer sheets) and document the conservative choice in the entry's `description` field (NOT in `tags`).
- **Schema edits require validator regen.** `pnpm precompile:validators` regenerates `libs/domain/catalog/src/validator.generated.cjs` (committed). CI fails on a schema edit without regen via `git diff --exit-code` of the generated file.
- **Additive `textures` field (3D-fidelity Bucket 2).** `SubstrateEntry` / `HardscapeEntry` / `PlantEntry` gain optional `textures?: { albedo?, normal?, roughness? }` (shared `CatalogTextureRefs` type + `#/$defs/CatalogTextureRefs` schema def) — catalog manifest schemaVersion stays at 3, same precedent as `EquipmentEntry.flow?`. Each ref is a relative PNG file name matching `^[a-z0-9._/-]+\.png$`, resolved by the 3D renderer as `baseUrl + ref` against the catalog texture root (host serves `libs/domain/catalog/assets/textures/` at `assets/catalog-textures/`); the 2D renderer ignores the field, and an absent block = the procedural-only pre-Bucket-2 look (no loader defaulting — pure pass-through, unlike `coverScore`). Core manifests use the family file-name convention `<family>.{albedo,normal,roughness}.png` with families `stone-gray` / `stone-warm` / `stone-dark` / `wood-bark` / `soil-dark` / `sand-fine` / `gravel-mixed` / `leaf-fine` / `leaf-broad`, generated by `tools/generate-textures.mjs`. `tools/validate-catalog.mjs` warns (never fails) on a ref with no matching file, and tolerates the texture root not existing. **Livestock is deliberately excluded:** per-species texture maps fight the one-InstancedMesh-per-archetype batching in `livestock-renderer-3d` (per-instance data is limited to attribute slabs) — deferred, tracked in `plans/3d-fidelity-followups.md`. `additionalProperties: false` on the block catches manifest typos at load time.
- **Additive `light` block (3D overhead equipment lighting).** `EquipmentEntry.light?` (`{ lumens?, colorTempK?, beamAngleDeg?, fixtureLengthMm? }`) is additive — catalog manifest schemaVersion stays at 3, same precedent as `flow` / `airRateMl` / `photoperiodHours`. It drives the 3D renderer's overhead equipment lighting (one SpotLight + fixture mesh per attached `category: 'light'` equipment); the renderer supplies defaults for every absent subfield, so there is **no loader defaulting — pure pass-through** (like `textures`, unlike `coverScore`). Only meaningful when `category === 'light'`; ignored otherwise. **No fabricated specs:** omit `lumens` for PAR-only vendors (Kessil, ADA publishes a lm range — the core manifest records the conservative low bound and says so in `description`), record the documented mid-point when a manufacturer publishes a CCT _range_ (and document the mid-point choice in `description`), and omit `beamAngleDeg` when unpublished. Bounds: `lumens` > 0, `colorTempK` in [1000, 20000], `beamAngleDeg` in (0, 180], `fixtureLengthMm` > 0; `additionalProperties: false` catches manifest typos at load time.
- **`decor` kind (GLB-modelled classic ornaments).** A sixth `oneOf` branch — catalog manifest schemaVersion **stays at 3** (purely additive: no existing branch changes; pre-decor readers surface a per-entry validation error for the unknown kind — the loader never silently drops it). `model` is a REQUIRED relative GLB ref matching `^[a-z0-9._/-]+\.glb$`, resolved by the 3D renderer as `baseUrl + ref` against the catalog **model root** (host serves `libs/domain/catalog/assets/models/` at `assets/catalog-models/` — see the `apps/web/project.json` asset glob); the 2D renderer ignores it and paints the hardscape-convention `color` + `silhouette` baseline instead. There is deliberately **no `textures` block on decor** — the GLB carries its own authored PBR materials, so the triplanar catalog-texture pipeline doesn't apply. `coverScore` is loader-defaulted by category like hardscape: **structure → 0.6, wreck → 0.5, bones → 0.4, ruin → 0.3** (decorations have swim-through cavities, unlike flat hardscape `other` decor at 0). `tools/validate-catalog.mjs` **warns (never fails)** on a `model` ref with no matching file under the model root and tolerates the root not existing (the GLB baker runs separately — mirror of the texture-ref handling). Core decor entries are **generic archetypes of the classic resin ornaments** — no brand names, no fabricated manufacturer specs; `naturalSize` is the authored model's bounding box (the GLB is authored to exactly that box at `transform.scale = 1`). Id convention: dot-namespaced `decor.<name>` (e.g. `decor.treasure-chest`), matching the rest of the core catalog.
- **Additive equipment fields (Stage 11 F11.5).** `EquipmentEntry.flow?` (`{ outflowPos?, outflowVec?, intakePos?, flowRate? }`) and `EquipmentEntry.airRateMl?` are additive — catalog manifest schemaVersion stays at 3. The `flow.outflowPos` / `outflowVec` / `intakePos` Vec3s are re-declared inline in the catalog schema (`#/$defs/Vec3`) rather than imported from `domain/geometry` to keep the catalog runtime free of geometry deps. `additionalProperties: false` on both the `flow` block and its Vec3 subfields catches manifest typos at load time.
